# Резервное копирование Loom

В Loom предусмотрено два уровня резервного копирования. Они решают разные задачи
и дополняют друг друга.

## Переносимая копия Loom

В боковой панели нажмите кнопку **«Резервная копия»**, затем
**«Скачать JSON»**. Браузер сохранит файл вида:

```text
loom-backup-2026-08-03T10-30-00-000Z.json
```

Копия содержит:

- проекты и их свойства;
- задачи и подзадачи;
- текстовые материалы;
- связи материалов с проектами и задачами;
- метаданные PDF-материалов.

Для восстановления откройте то же окно, выберите JSON-файл, проверьте количество
проектов и материалов и нажмите **«Восстановить»**. Перед заменой текущих данных
Loom запросит подтверждение.

### Версии формата

Файл не повторяет устройство таблиц Supabase. Он содержит логическую модель Loom
и служебные поля:

```json
{
  "format": "loom-workspace-backup",
  "formatVersion": 1,
  "schemaVersion": "202607300001",
  "createdAt": "2026-08-03T10:30:00.000Z"
}
```

`formatVersion` — версия переносимого формата. При будущих изменениях базы новая
версия Loom должна сохранять адаптеры чтения старых форматов. Поэтому уже созданные
копии не следует переписывать или «обновлять» вручную.

`schemaVersion` помогает определить, при какой схеме базы была создана копия, но
восстановление не зависит напрямую от названий таблиц и столбцов.

Loom также умеет импортировать ранний JSON без служебного заголовка, если внутри
находятся массивы `projects` и `materials`. После чтения такой файл преобразуется
в текущую модель.

### Ограничение PDF

Сами PDF-файлы находятся в Supabase Storage и в JSON-копию базы не входят. В ней
сохраняются только их имена, пути и связи. Для полной автономной копии PDF нужно
дополнительно выгрузить бакет `materials`. В дальнейшем переносимый формат можно
расширить ZIP-контейнером; его новая версия при этом не отменит поддержку JSON v1.

## Полный технический снимок Supabase

Такой снимок нужен для аварийного восстановления всей базы или переноса в другой
проект Supabase. Для него нужны Docker Desktop, Supabase CLI, строка подключения
к базе и пароль базы данных.

Создайте отдельную папку и выполните:

```powershell
npx supabase db dump --db-url "<CONNECTION_STRING>" -f roles.sql --role-only
npx supabase db dump --db-url "<CONNECTION_STRING>" -f schema.sql
npx supabase db dump --db-url "<CONNECTION_STRING>" -f data.sql --use-copy --data-only -x "storage.buckets_vectors" -x "storage.vector_indexes"
```

Храните вместе четыре составляющие версии снимка:

```text
backup-2026-08-03/
  roles.sql
  schema.sql
  data.sql
  migrations/       копия supabase/migrations из того же коммита
```

Имя папки лучше начинать с даты и дополнять хешем Git-коммита. Миграции рядом со
снимком объясняют структуру данных на момент создания и позволяют воспроизвести
дальнейшие изменения.

Восстанавливать SQL-снимок безопаснее сначала в новый или локальный проект, а не
поверх рабочей базы. Для нового проекта используется `psql`:

```powershell
psql --single-transaction --variable ON_ERROR_STOP=1 --file roles.sql --file schema.sql --command "SET session_replication_role = replica" --file data.sql --dbname "<NEW_CONNECTION_STRING>"
```

После проверки следует заново включить публикации Realtime и убедиться, что
миграционная история соответствует сохранённому каталогу `migrations`.

Полный SQL-снимок также не содержит бинарные объекты Supabase Storage. Их нужно
архивировать отдельно.

## Рекомендуемая схема

- После важных изменений данных скачивать переносимую JSON-копию Loom.
- Периодически создавать полный SQL-снимок и копию Storage.
- Хранить минимум одну копию вне компьютера и вне самого проекта Supabase.
- Не удалять старые JSON-файлы: номер формата позволяет будущим версиям Loom
  распознать и преобразовать их.
